# Architectural approach notes

## Миграция на микросервисную архитектуру. Strangler Fig.

При миграции (ESB ->  EDA, DWH -> Data LakeHouse) необходимо провести рефакторинг существующих сервисов и перевести их с парадигмы  клиент-сервер на producer-consumer и новую парадигму взаимодействия (Event-Driven architecture).

- Будем использовать микросервисный подход, нативно поддерживающий облачную архитектуру, EDA и независимость разработки.
- Перевод функциональности на новые сервисы планируется по паттерну Strangler Fig для постепенной и безопасной миграции "по кусочкам". Система должна функционировать непрерывно, а риски минимизированы.
- Бизнес-логика DWH/ESB, включая валидацию и проверки, будет вынесена в отдельные сервисы согласно DDD для независимого дальнейшего развития.
Бизнес логика новых подключений (компания электронного оборудования, и т.д.) не будет добавлена в DWH и сразу же будет реализованна в виде доменных микросервисов на новых общих принципах.
- Все функции DWH в конечном итоге должны быть заменены новыми масштабируемыми backend микросервисами и новым хранилищем по типу Data LakeHouse, обеспечивающим масштабируемое хранение всех типов данных, включая неструктурированные, и удобство их использования для аналитики.
- DWH и ESB планируется к полному выведению из IT ладшафта только после полноценной и подтвержденной миграции.

## ACL
С учетом использования Strangler Fig нам понадобятся ACL (анти-коррупционные слои) на время миграции и фича-тоглы для возможности гибкого переключения функциональности со старого на новый сервис и обратно при необходимости.
Они изолируют новые микросервисы от старой системы, обеспечивая преобразование данных и маршрутизацию при необходимости обращения новых сервисов к еще не мигрировавшим функциям/API. Сюда же попадает валидация.

ACL выполняет роль адаптера и маршрутизатора.
Взаимодействие новых сервисов со старыми в процессе миграции происходит только через ACL, внутри которого также осуществляется необходимая маршрутизация по принципу _API шлюз_ (reverse proxy будет недостаточно с учетом сложных ESB правил).

С учетом использования Apache Camel в старой архитектуре, ACL может использовать Apache Camel framework, который может помочь в преобразовании/адаптации данных между новыми и старыми форматами (см. паттерны facade и adapter).

## Маршрутизация между сервисами
Между новыми сервисами, а также между новыми сервисами и ACL до окончания процесса миграции, маршрутизация использует новый брокер сообщений - Apache Kafka.

- Полностью асинхронное взаимодействие при помощи передачи событий.
- Разные домены будут использовать различные партиции и топики.
- Перепосылки.
- Также Kafкa позволит организовать хранение непрочитанных сообщений.
- Отдельными топиками в доменах реализуем Dead Letter Queue

## Маршрутизация между фронтендами и системой.

Используем стандартный подход API GW. Весь траффик от фронтендов будет проходить через него и маршрутизироваться по определенным правилам. Так же сюда будет встроен rate limiting и маршрутизация на сервисы авторизации. По мере отладки автоматического масштабирования rate можно увеличивать.

## Интеграция между сервисами
Для интеграции запланируем хореографию сервисов по принципу Saga с возможностью отката всех предыдущих шагов неудавшихся операций в других сервисах.
Это усложнит реализацию, но в штатном режиме повысит производительность и сохранит максимальную независимость сервисов, что является бизнес целью. Также позволит устранить единую точку отказа (по сравнению с оркестрацией откатов одним сервисом).
