


# Архитектурные риски

## Риск непрерывности обслуживания при миграции

Вероятность: высокая
Влияние: высокая

Меры:
- Разработка плана перехода (поэтапное переключение и откат)
- Использование метода parallel run c постоянным мониторингом.
- Обеспечение наблюдаемости с первых шагов перехода.

## Несоответствие новой архитектуры бизнес‑требованиям
Вероятность: средняя.
Влияние: высокое.

Меры:

- вовлечение бизнес‑заказчиков в проектирование, прототипирование.
- сопоставление технических и бизнес показателей, чек-лист (https://code.s3.yandex.net/software-architect/12.pdf?etag=14076d49abb554a44922373dce09c015)
 - эксперименты (с использованием тестов, фича-тоглов).
 - Привлекать межфункциональные команды.


## Наличие проблем в старой архитектуре, которые могут ухудшить показатели новой системы при миграции.
Вероятность: средняя
Влияние: высокое

Меры:
- Выявление узких мест в старой системе с использованием метрик.
 - Разработка новых метрик.
 - Мониторинг и логирование. Повышение наблюдаемости.

## Узкие места производительности, недооценка нагрузки.
Вероятность: средняя.
Влияние: среднее.

Меры:
- Нагрузочное тестирование на ранних этапах, мониторинг метрик.
- Проектирование решений на основе выявленных проблем c использованием HLD, Brunch by abstraction, Parallel Run.
- Разработка плана перехода (поэтапное переключение и откат)


## Риски вносимые рефакторингом

Вероятность: высокая
Влияние: высокое

Меры:
 - Использовать метод brunch by abstraction
 - Поэтапное переключение.


## Ошибки из-за непонимания целостной картины (сложность архитектуры).

Вероятность: средняя
Влияние: средняя

Меры:
- Использование HLD повысит общее понимание, хотя и потребует большего времени.


## Риск несогласованности данных между старыми и новыми хранилищами

Вероятность: высокая
Влияние: высокое

Меры:
 - Организация треугольника взаимодействия (общей группы): совместно прорабатывать архитектуру миграции, настраивать понятные потоки репликации, разрабатывать единый интерфейс взаимодействия.

## Недоучет важности разработки мониторинга - риск несвоевременного обнаружения проблем
Вероятность: средняя
Влияние: среднее

Меры:
 - Либо выделить команду, либо в каждой команде иметь людей с компетенцикй в observability. Подходы стандартизовать.
